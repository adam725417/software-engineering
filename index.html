01

什麼是軟體工程？

寫出能執行的程式，只是軟體工程的一部分。真正的目標是把模糊的問題，轉變為可信賴且可維護的系統。

WHAT

軟體 ≠ 程式碼

一套系統除了程式碼，還包括需求、資料、介面、架構、測試、部署文件及持續維護。

WHY

解決真實問題

軟體工程關心的是使用者價值、可靠性、成本、時程與變更，而不只是功能做得出來。

HOW

工程化的方法

建立可以溝通、追蹤、驗證與反覆改進的開發流程，降低不確定性與錯誤風險。

同一個問題，兩種思考

使用者說：「我要一個庫存查詢網站。」

工程師還要問：誰能查？資料多久更新？查無資料如何顯示？庫存為負數怎麼辦？多久回應？要不要匯出？

四種非功能需求

可靠性：錯誤不會破壞資料。

安全性：不同角色有不同權限。

效能：大量資料仍可及時回應。

可維護性：規格改變時能容易修改。

重點：AI 可以快速生成程式，但「需求究竟對不對」仍需要人來確認。
想一想

問：為什麼「網頁可以開啟」不代表系統完成？答：它可能沒有驗證資料、處理例外、檢查權限，也未滿足效能及維護需求。

DEEP DIVE · 研究所延伸

從「會寫」到「可交付」

需求的三種層次

商業需求：為何要做？使用者需求：誰在何時需要什麼？系統需求：哪些輸入、輸出與限制必須被滿足？以庫存查詢為例，「降低盤點時間」是商業目標，「查詢料號庫存」是使用者需求，「空白料號如何處理」才是可驗收規格。

六種工程產物

需求文件（SRS）、使用情境（Use Case）、資料模型、架構圖、測試案例、部署與維護紀錄。每項產物都要有版本和責任人，AI 生成不等於自動核准。

兩種非功能需求

效能：在明確資料量與測試環境下量測回應時間。安全：限制輸入、權限與敏感資訊外洩。另要考慮可用性、可觀測性、可維護性與備援。

課堂挑戰 ✦

案例練習：把「做一個好用的庫存系統」改寫成 3 條可測試需求；每條包含前置條件、輸入、期望輸出、失敗情境。

02

正向工程 vs. 逆向工程

用同一個「庫存查詢系統」比較兩種工程方法，避免把逆向工程誤解成直接複製介面。

FORWARD ENGINEERING / 正向工程

從需求建立系統

庫存需求
→
欄位與規則
→
網站程式
  1. 訪談使用者，列出查詢與權限需求。
  2. 設計資料欄位、API 與介面。
  3. 撰寫程式、測試並部署。
REVERSE ENGINEERING / 逆向工程

從系統理解規格

現有網站
→
觀察與證據
→
推導設計
  1. 操作查詢欄位，記錄輸入與輸出。
  2. 觀察例外情境、資料流與執行行為。
  3. 還原可驗證的功能規格與架構假設。

關鍵概念：逆向 ≠ 複製 ≠ 重建

概念目的可能的產出
逆向工程理解既有系統如何運作需求、流程、資料模型、架構推測
重新實作根據已知或推導規格建立新系統另一套程式與操作介面
系統現代化改善舊系統的技術與維護條件可遷移、可測試的新版本
企業情境：舊 MES 系統文件不完整時，可透過具授權的介面觀察、日誌、API 與現有程式分析，補足規格文件；但不能僅憑畫面便認定已掌握所有後端規則。
進階思考：規格還原是否有唯一正解？

不一定。不同內部實作可能產生相同行為。逆向工程常只能根據可取得的證據縮小假設，不能保證還原原始程式架構。

DEEP DIVE · 研究所延伸

正向、逆向與重新實作的界線

正向工程 Forward Engineering

先取得需求，再選擇設計與技術，經由實作和測試交付。重點在將意圖變為可驗證的產品。

逆向工程 Reverse Engineering

從合法取得的系統證據推論規格、結構及資料行為。相同輸出可能來自不同內部設計，因此還原的是有證據支持的理解，不保證找出原始實作。

重新實作 Reimplementation

將逆向推得的需求再經正向工程實現；需額外驗證相容性、安全、效能與權利限制。重新做出相似 UI 不代表邏輯一致。

課堂挑戰 ✦

思辨練習：兩個網站都能查到 120 件庫存，但一個從快取取值，另一個從資料庫即時查詢。外觀一致，能說它們同一個系統嗎？

03

黑箱、灰箱與白箱分析

逆向分析的深度，不只是工具好不好，而是你合法取得多少資訊，以及證據能支持什麼結論。

BLACK BOX / 黑箱

看得到輸入與輸出

觀察介面、操作回應、錯誤提示、效能表現。

適合：只有網站操作權限時

限制：看不到內部演算法與資料模型。

GRAY BOX / 灰箱

知道部分內部資訊

除操作外，另取得部分 API 文件、日誌、資料結構或有限權限。

適合：跨系統整合、維護與除錯

限制：資訊仍不完整，推論需標註。

WHITE BOX / 白箱

可檢視內部實作

在合法授權下檢查原始碼、呼叫流程、資料庫結構與測試。

適合：原始碼維護、程式碼審查

限制：看得到程式，也未必知道原始業務意圖。

練習：下列證據能支持哪些結論？

觀察到的證據合理結論不能直接推論
輸入空白搜尋，顯示「請輸入編號」介面存在空值驗證行為驗證一定是在後端完成
瀏覽器網路請求顯示 /api/inventory目前流程使用該網路端點全部庫存功能只靠這一支 API
程式庫出現 SQL 查詢字串程式包含相關查詢邏輯所有執行路徑都會呼叫它

證據分級

🟢 已觀察
Observed
🟡 合理推論
Inferred
⚪ 尚未確認
Unknown

請 AI 報告分析時，每一項結論都標註這三種狀態，並列出「需要何種驗證才能升級為已觀察」。

DEEP DIVE · 研究所延伸

用證據限制 AI 的推論

黑箱：行為矩陣

設計輸入等價類：完整料號、部分料號、空字串、前後空白、特殊字元、不存在資料、重複查詢。記錄輸入→輸出→截圖／時間戳。

灰箱：介面契約

若合法取得部分 API 文件、回應碼、日誌或資料欄位，可交叉驗證推測；部分資訊不保證觀察到全部內部邏輯。

白箱：程式與資料流

合法取得原始碼時，可讀取資料流程、依賴、分支與例外處理；仍須執行測試，因為程式碼存在不等於功能實際上線。

課堂挑戰 ✦

證據練習：觀察到「輸入 A10 能查出 A1001」，可以確認支援模糊查詢；但不能據此認定使用 SQL LIKE。請標記「已觀察／推論／未確認」。

04

AI 在軟體生命週期中的角色

AI 不是只在最後幫忙寫程式。它可以參與每個階段，但每個階段的責任、輸入與驗證方式都不同。

01 / DISCOVER

需求分析

產出：訪談題綱、使用者故事、驗收條件、邊界情境。

人要確認：業務規則是否正確？

02 / DESIGN

系統設計

產出：模組清單、資料表草案、API 契約、架構選項比較。

人要確認：安全、擴充、成本與限制。

03 / BUILD

程式開發

產出：前端頁面、後端程式、測試資料、程式碼解說。

人要確認：依賴套件、權限、秘密資訊。

04 / TEST

測試驗證

產出：測試案例、單元測試、錯誤原因假設、修復建議。

人要確認：測試是否獨立、足夠、有覆蓋關鍵風險。

05 / OPERATE

部署維護

產出：操作手冊、部署檢核、日誌摘要、異常排除建議。

人要確認：上線風險、回復方案、監控。

CORE PRINCIPLE

AI 生成 ≠ 工程驗收

當 AI 產出更快時，錯誤也可能更快進入正式系統。必須留下人為審核與可追蹤的驗證證據。

新世代的工具觀念：Agent + 逆向工具 + 驗證工具

AI Agent
規劃與工具呼叫
→
分析工具
搜集可取得證據
→
模型推論
提出假設
→
測試工具
驗證與修正

各工具的適用性與授權限制需分別確認，並非每個案例都能自動完成。

可直接複製的研究型 Prompt

1. 列出可直接觀察的功能、輸入、輸出及錯誤訊息。
2. 將結論分為「已觀察 / 合理推論 / 尚未確認」。
3. 產出功能需求清單及至少 8 個驗收測試案例。
4. 不要捏造資料表、後端框架或 API。
5. 對尚未確認的項目，提出下一步驗證方法。
以 Markdown 表格回答，附每項結論的證據來源。
DEEP DIVE · 研究所延伸

AI 協作應有的檢查點

需求：AI 當訪談助手

產出角色、目標、驗收條件，並列不確定項目。檢查：利害關係人確認、規格一致性、無臆測業務規則。

設計與實作：AI 當副駕

比較不同架構的取捨、生成模組與測試骨架。檢查：介面契約、資料保護、授權套件、人工程式碼審查。

測試與維運：AI 當分析師

產生測試資料、分析錯誤記錄、提出根因假說。檢查：以獨立測試資料驗證、不把模型推測當真因、不上傳機密日誌。

課堂挑戰 ✦

進階練習：設計 AI 使用政策，將「可直接使用」、「須人工審核」、「禁止輸入 AI」各列 2 項企業實例。

06

AI 生成軟體的品質評估

從「看起來很像」進步到「有客觀測試證據」。研究所課程要討論品質衡量方法，而不只展示成果。

功能正確性

是否符合已確認的需求與預期輸出？

證據：測試案例、通過率、錯誤清單

可維護性

命名清楚嗎？是否模組化？有測試與文件嗎？

證據：程式碼審查、變更成本

安全性

是否安全處理輸入？權限與機密資訊是否受保護？

證據：安全檢查、測試與人工審查

效能與穩定性

資料量成長、非預期輸入時會如何？

證據：回應時間、負載與失敗率

交付成本

不只是 AI 生成時間，也含除錯、測試、部署與後續維護。

證據：總投入工時與成本估算

可追溯性

規格、Prompt、程式版本、測試與修正，有沒有留下紀錄？

證據：需求—測試—結果對應表

課堂示範評分規準（100 分）

評估面向配分評分依據
功能正確性30已確認的案例通過與否，包含邊界情境
需求與證據20觀察／推論區分清楚、需求可追溯
安全與可靠性20輸入處理、錯誤行為、安全審查
可維護性15可讀性、結構、註解及修改難度
成本與反思15記錄實際工時、工具限制與改進方法

「驗證迴圈」：別停在第一個答案

提出假設
→
設計測試
→
執行測試
→
對照證據
↺
修改假設

以 CSV 匯出功能示範：除了能產出 CSV，還要驗證中文編碼、特殊字元、換行、公式注入風險與不同軟體開啟時的行為。

延伸問題：AI 能自行評定自己的品質嗎？

AI 可以協助生成測試與審查建議，但如果程式、測試與評分均由同一模型產出，可能共用錯誤假設。重要測試應依獨立規格、實際操作與人類審查進行。

DEEP DIVE · 研究所延伸

從單一分數到品質證據鏈

正確性 Correctness

區分預先公開的練習測試與保留的隱藏驗收測試；通過率＝通過案例／總案例，但須按重要性追蹤關鍵失敗。

維護性 Maintainability

讓另一組學生新增「低庫存警示」；比較改動時間、回歸測試失敗及程式結構，而非單看程式碼行數。

安全與成本 Security / Cost

檢查 DOM 注入、資料暴露、第三方依賴，並記錄模型／Token 成本、人工分析時間、返工次數。成本不只包含 API 金額。

課堂挑戰 ✦

分析練習：假設 A 組 10 題過 8 題、修正 9 次；B 組 10 題過 9 題、修正 4 次。這能證明 B 法更好嗎？討論樣本、隨機化與差異顯著性。

07

研究生討論：AI 能取代工程師嗎？

這不是單選題。從技術能力、企業管理、專業責任三個層面，分析哪些工作被自動化，哪些能力反而更加重要。

TECHNOLOGY

技術層面

AI 擅長產生樣板、說明程式與提出修復方案，卻可能誤解未明確描述的需求、過度自信或忽略邊界條件。

討論：哪些工作可委由 AI？哪些必須人工驗證？

分組辯論（每組 4–5 人）

題目：「五年後，企業是否仍需要專職軟體工程師？」

  1. 正方：AI 大幅降低編碼成本，許多標準化工作被自動化。
  2. 反方：高風險系統的需求、架構、資安與維運仍高度依賴專業。
  3. 評論組：提出工作重新配置的混合模型，而非僅回答取代或不取代。

交付：用一個真實企業流程舉例，提出三項可交給 AI 的任務、三項必須人員把關的任務，並寫出衡量成效的 KPI。

課程結論：AI 降低編碼門檻，卻提高了「定義正確問題、建立證據、對結果負責」的重要性。

技術論點

例行 CRUD、單元測試草稿與程式說明容易被加速；複雜需求歧義、跨系統整合、安全事故決策仍依賴負責任的判斷與驗證。

管理論點

AI 產能提高不代表總交付成本等比例下降。規格、審查、測試、部署、維運與責任歸屬仍會產生成本。

組織論點

可能出現「產品／領域專家＋AI 協作開發＋工程審查」的分工。評估重點應由程式碼產量轉向交付品質、故障率與需求滿足。

A/B LAB｜直接生成 vs. 規格導向開發

同樣的目標網站、工具、資料與時間，對比不同開發流程是否影響品質。這是課堂準實驗，不是預先證明工程方法必勝。

TEAM A · DIRECT GENERATION

直接生成組

觀察原網站後，直接用 AI 實作。可補問、測試與修改，但不必先交正式需求規格。

  1. 操作原站並向 AI 描述。
  2. 生成第一版網站。
  3. 測試、修正、記錄。
TEAM B · SPECIFICATION FIRST

逆向分析組

先產出附證據的 SRS，經組內確認才請 AI 實作。分析時間也計入總時間。

  1. 系統性黑箱觀察。
  2. 整理 SRS 與驗收條件。
  3. 生成網站、測試、修正。
CONTROL VARIABLES · 公平比較

必須一致

模型版本、可用工具、網站及資料、實作語言、時限、允許提示次數之規則、驗收案例與評分人員。

避免偏誤

依 AI 與程式先備能力分層隨機分組；有餘裕時用多小組，或第二輪換題、交叉設計，避免單次 A/B 兩組下因果結論。

正式紀錄

首次成功執行時間、通過驗收時間、修正迴圈、功能測試通過率、Prompt 次數、模型支出與人工操作時間。

Agent｜調查員

負責提問、規劃工具呼叫與組織分析報告；不是靜態分析引擎本身。

MCP｜工具接線規格

Model Context Protocol（模型上下文協定）讓 Agent 呼叫外部工具。沒有連線驗收，不代表裝好 Skill 就能直接使用。

REA｜分析工具集合

Reverse Engineering Agents 可透過 CLI 或 MCP 使用能力；本課先執行 JavaScript 靜態分析，再談 Agent。

Evidence｜查證收據

保存 JSON、檔案位置、檢查限制。雜湊用來比對輸入身分，並不等於推論已被證明。

01 renderer.js

靜態分析 Static Analysis
不啟動 App，讀取程式檔建立模組與 IPC 關係。優勢是可重複查證，限制是無法證明實際執行路徑。
動態驗證 Runtime Validation
真正啟動自己撰寫的 App，點擊 Ping，觀察是否輸出 pong:HELLO。執行時錯誤、權限與環境仍可能影響結果。


手把手 LAB｜從六檔程式到 Trace Evidence
先備：自有電腦、支援版本 Node.js、終端機及網路；沒有環境的同學可先完成上方的線索追查與證據判讀。本文參考的案例曾使用 REA 6.0.0，但不同環境請以實際 CLI help 為準。


  1. 下載教材：取得 ZIP 內的 rea-demo/ 六檔範例與 make-trace.cjs，確認 main.js、preload.js、renderer.js、format.js。
  2. 環境檢查：node --version、npm --version 與 npx -y rea-agents@6.0.0 --help。
  3. 收集完整 Evidence：在範例資料夾執行下方對應系統的指令，分離 JSON 與 stderr；注意分析檔輸出到上一層。
  4. 生成追查請求：在上一層執行 node make-trace.cjs，種子必須是 kind: "channel"、value: "demo:ping"。
  5. 追查與核對：使用 trace-application-feature，比較 invokes、handles 與原檔；輸出可達關係圖不代表已經執行。
  6. 延伸：有興趣才選擇啟動 Electron 驗證 UI；或先看 Claude Code MCP 的唯讀 setup 計畫，再決定是否套用。

Evidence Lab｜你找到的究竟是哪一種證據？
請依序完成四道證據判斷題。


常見失敗：invalid_request
檢查 details.issues，以及 seed 的 kind 是否用 channel 而非圖節點名稱 ipc-channel。
常見失敗：timeout
先區分 Agent 客戶端等待、工具執行時間與原生引擎啟動時間；不要把某個引擎的時限套到所有 REA 指令。
常見失敗：原生引擎
本單元的 JS 範例不需要 Hopper 或 Ghidra。若進階原生分析失敗，保存版本、stderr、雜湊與錯誤碼。
安全與退出
只分析自己的或經授權的程式；避免金鑰與機密資料。CLI 分析與 Agent 模型服務是不同的資料邊界。接入 MCP 前先檢查變更與回復方式。
